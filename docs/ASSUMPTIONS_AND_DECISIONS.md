# Assumptions and Decisions Log

Every call made while scaffolding this project without asking first, and why — so any of these can be overturned cheaply once you disagree, instead of being archaeology later.

| Decision | Why | Easy to reverse? |
|---|---|---|
| ~~Backend is Firebase Cloud Functions running one Express app~~ — **superseded, see below** | | |
| **Confirmed by user (2026): backend is a plain Node.js/Express server (`app.listen`), not Cloud Functions, deployed to a free Node host (Render/Railway/Vercel/etc.)** | Explicit user instruction — avoids Cloud Functions' Blaze-plan requirement entirely, since Firestore/Auth/Storage all run on Firebase's free Spark plan and only compute would have forced an upgrade | Medium to reverse back to Cloud Functions later — the layered Express structure (routes/controllers/services/repositories) is unaffected either way, only `index.js`, `config/firebaseAdmin.js` (now needs an explicit service account, no ambient GCP identity), and the upload-processing flow changed |
| No Cloud Functions Storage trigger or Cloud Tasks queue — reference analysis uses client-registers-upload, confirmed | Direct consequence of the plain-server decision above — neither GCP-native mechanism is available outside Cloud Functions | N/A |
| **Open, not decided:** how the queue actually gets *processed* — a cron-hit `/internal/process-analysis-queue` endpoint (works on any host, including serverless-style ones) vs. a long-running worker process that polls Firestore in a loop (needs a host that keeps a process alive) | User explicitly deferred this until the backend host is picked — docs currently describe the cron-hit shape as the leading option, not a locked-in decision | Whichever is chosen, it's isolated to the queue-processing endpoint/worker — doesn't touch the register-upload endpoint or anything else |
| Backend language is plain JavaScript (CommonJS), not TypeScript | Matches README's literal "Node.js" framing and the playbook's JS-flavored examples; lowest setup friction | Medium — migrating to TS later is mechanical but touches every file |
| Frontend is feature-first (`lib/features/*/data,domain,presentation`) from day one, not the flat `controller/model/views` starter shape | Six-plus feature areas are already named in the README roadmap before a single screen exists — the flat shape would need migrating almost immediately | Low cost either way since nothing is built yet; flat shape was never started |
| State management: `Provider` + `ChangeNotifier`, not `GetX`, for v1 | Playbook default for small/medium apps; no evidence yet that this app needs GetX's extra machinery | Yes — playbook's own replacement matrix covers this migration path |
| Networking: `dio`, not plain `http`, from the start | Video upload needs progress callbacks and the auth-token interceptor is needed on day one, which `http` doesn't give cleanly | N/A, already the right call per playbook's own replacement rule |
| Search: tokenized `searchTerms` field + `array-contains-any`, not Algolia/Typesense, for v1 | Zero new infra/cost; README's search promise doesn't specify ranking quality, just "searchable" | Yes — swap-in point is isolated to the repository query method |
| Video clip trimming (Expression Vault): client-side trim-and-reupload first, server-side ffmpeg only if needed | Avoids committing to a dedicated ffmpeg worker process/service before confirming client-side quality is insufficient | Yes |
| One-tap in-app screen recording is explicitly deferred past Phase 1 | Native engineering risk (MediaProjection + ReplayKit + iOS Broadcast Extension) is disproportionate to a Library sub-feature; README itself frames record-and-share as the correct v1 | N/A, this is a sequencing decision, not a technical lock-in |
| The Radar / Format Arbitrage Board got no schema or endpoints | README explicitly flags this as legally-gated (licensed data only, no scraping) | N/A, intentionally not started |
| Payments/checkout sections of the base playbook (12, parts of 10/13) are ignored | Foolscap has no payment flow; the playbook was written in e-commerce vocabulary and says to follow project constraints over the letter of the guide when they conflict | N/A |
| Three fully separate Firebase projects (dev/staging/prod) instead of one project with env prefixes | Full data isolation; a dev-only bug can't touch staging/prod Firestore data | Yes, but costly to redo once data exists — worth confirming early |
| **Confirmed by user (2026, mobile-only pivot):** Flutter builds are Android/iOS only — no Flutter Web, no desktop, ever, not just for v1 | Explicit user instruction | N/A, this is now a hard constraint, not a sequencing choice |
| The Pitch public link is a server-rendered HTML page from the backend (`GET /pitch/:token`), not a Flutter screen | Direct consequence of mobile-only: a client reviewing a pitch can't be assumed to have the app installed, so the one surface that needs "any browser, no install" was never going to be solved by adding a Flutter Web build | Low — it's an additive backend route, doesn't block anything else |
| Brand Bible (`clients/{cid}`) expanded from 6 flat fields to a 7-section structured document (identity, voice & tone, language rules, audience, products, pillars, competitors) plus `brandBibleVersion` | User asked to treat Foolscap holistically as a content platform, not just a script tool — the Brand Bible is the one document every other feature (linter, heatmap, script defaults) reads from, so it's the highest-leverage place to add depth | Medium — it's additive (all new fields optional/partial), but the *frontend* settings screen for it hasn't been built yet, so now is the cheap time to get the shape right |
| Did **not** add a content-calendar/scheduling collection or an analytics rollup, despite "content platform" framing | Nothing in README's roadmap asks for scheduling or analytics yet; `scripts.status` + `retros/{rid}` already cover "did it go out" and "how did it do" — adding more would be scope creep beyond what any feature actually consumes | N/A — can revisit if a specific feature ends up needing it |
| Brand Bible's `competitors` and claim-adjacent fields (`approvedClaims`, `competitorMentionPolicy`) are config-only, stored now even though the linter logic that reads them is Phase 4+ | Storing the list isn't scraping (unlike Radar) and costs nothing; building the data model early avoids a second reshape when Phase 4/5 arrives | Low |

If any of these turn out wrong, update the row and the corresponding doc section together — don't let this log drift from what the code actually does.
